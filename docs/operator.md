# Reference operator

`src/selfront.py` implements Sections 2 and 3 over a stable bottom-layer graph. IDs are contiguous integers; each adjacency list contains distinct valid IDs. Vectors and the query have matching dimensions and finite coordinates. The graph and predicate set remain unchanged during the invocation. Eligibility is a materialized set supplied by the caller.

`search(vectors, adjacency, eligible, query, entry, k, ef, seed, scheduler, cfg, trace)` returns IDs, squared distances, a fallback flag, counters, and an optional trace. Set `scheduler=False` for native BPF ordering. Each invocation creates fresh discovery and heap state. `Config` contains the paper's default scheduler parameters. The JSON input used by `scripts/run_example.py` has these search argument fields and an optional human-readable `description`; configuration is supplied separately with `--config`.

The candidate heap C is ordered by distance and ID. W retains the best `ef` discovered vertices; R retains the best `k` eligible discoveries. An unseen neighbor is marked discovered and evaluated once even if W rejects it. Eligible discoveries update R independently of W admission. Candidates remain pending after eviction from W. The native minimum's distance is tested against W's worst distance before extracting a window; equality does not trigger stopping. A full W admits only a strict distance improvement, as specified in the paper; equal-distance arrivals do not displace its existing entries. R resolves equal-distance result ties by ID.

A scheduled decision considers at most `w=4` candidates inside both the native bound and `(1+epsilon)*native_distance+tau`. If the window has one member it is expanded without probes. Every fourth expansion is native. Probe estimates are freshly computed using one advancing per-query random generator. For degree above `s=8`, positions are sampled with replacement; repetitions count repeatedly. For degree at most s, every neighbor ID is read exactly once. Probing changes no discovery bits, heaps, result entries, or distance counters. Its two counts are scaled by degree/reads. Zero degree has zero priority; other priorities use `Yhat/(c+a*d+b*Uhat)`. Score ties use distance then ID, including the all-zero window.

The first eight expansions are native. Each scanned eligible occurrence contributes to the gate denominator, including duplicates. An already-discovered eligible occurrence contributes to the numerator, evaluated before discovery changes. The next block is enabled when at least 32 eligible occurrences were observed and the duplicate fraction is at least .35. Later blocks have 64 expansions, with counters reset at each boundary. Native and scheduled steps both contribute. Baseline BPF does not maintain these counters. The optional trace adds diagnostic storage proportional to executed steps; without trace, scheduler-specific live state is O(w).

When native termination produces fewer than k results, an exact eligible scan returns up to k records. A full approximate result is not replaced merely because its recall is low. `graph_distances` counts entry and new bottom-layer discoveries; `fallback_distances` counts the separately executed eligible scan. `adjacency_reads` excludes probes, and `probe_reads` counts sampled or exact metadata positions. They are operation counts, not elapsed time estimates.

`route(n, eligible_count, k, pilot_eligible, beta)` implements the shared routing rule as a pure decision function. It asks for a pilot when necessary; the caller must supply the final native pilot's eligible count. It does not generate that count or claim to run HNSW. Routing and search are separate so neither an example graph nor a result archive silently substitutes for the production pilot.

The circular example deliberately uses an origin query and nearly equal unit-vector distances to make multi-candidate windows visible. It is a mechanism demonstration; exhaustive eligible distances independently compute its recall. Floating-point squared distances and then ID determine ties. It is not one of the four scale workloads.
